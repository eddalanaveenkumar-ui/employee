# Employee Management API

A Spring Boot REST API for employee registration and login, JWT-protected
employee and department lookups, profile/password management, attendance,
department-scoped task creation and lookup, and a personal dashboard. It uses
Spring Security, Spring Data JPA, and MySQL.

## Features

- Register employees against an existing department.
- Authenticate using an employee ID and password; issue a signed JWT.
- Log out by blacklisting the presented bearer token for the life of the process.
- Retrieve the signed-in employee's profile and dashboard.
- Change the signed-in employee's password.
- List employees in the signed-in employee's department and view a same-department
  employee by employee ID.
- View departments, attendance records, and tasks; create a task for an employee
  in the signed-in employee's department.
- Store passwords as BCrypt hashes.

This service does not currently include an administrator role, department
management endpoints, attendance/performance update endpoints, refresh tokens,
or API documentation generated by OpenAPI/Swagger.

## Getting started

1. Create the MySQL database:

   ```sql
   CREATE DATABASE employee_db;
   ```

2. Configure the datasource and JWT settings as described in
   [Configuration](#configuration).
3. Start the application from this directory:

   ```powershell
   .\mvnw.cmd spring-boot:run
   ```

   On macOS/Linux, use `./mvnw spring-boot:run`.

4. The API listens on `http://localhost:8080` by default. There is no separate
   health endpoint configured.

Hibernate is configured with `ddl-auto=update`, so it creates/updates entity
tables when the application starts. It does **not** insert departments. Add at
least one department before registering an employee, for example:

```sql
INSERT INTO departments (department_code, department_name)
VALUES ('ENG', 'Engineering');
```

Choose department codes that make sense for your environment; registration
requires an existing exact department code.

## Configuration

The defaults are in `src/main/resources/application.properties`. Spring Boot
environment variables can override the corresponding properties:

| Property | Environment variable | Default / purpose |
| --- | --- | --- |
| `spring.datasource.url` | `SPRING_DATASOURCE_URL` | Local MySQL `employee_db` URL |
| `spring.datasource.username` | `SPRING_DATASOURCE_USERNAME` | `root` |
| `spring.datasource.password` | `SPRING_DATASOURCE_PASSWORD` | Set this in the environment; do not commit it |
| `spring.datasource.driver-class-name` | `SPRING_DATASOURCE_DRIVER_CLASS_NAME` | MySQL JDBC driver |
| `spring.jpa.hibernate.ddl-auto` | `SPRING_JPA_HIBERNATE_DDL_AUTO` | `update` |
| `spring.jpa.show-sql` | `SPRING_JPA_SHOW_SQL` | `true` |
| `jwt.secret` | `JWT_SECRET` | Base64-encoded signing key; supply a secure value |
| `jwt.expiration` | `JWT_EXPIRATION` | `86400000` milliseconds (24 hours) |

Example PowerShell session (use your own credentials and generated key):

```powershell
$env:SPRING_DATASOURCE_URL = "jdbc:mysql://localhost:3306/employee_db?serverTimezone=UTC"
$env:SPRING_DATASOURCE_USERNAME = "employee_app"
$env:SPRING_DATASOURCE_PASSWORD = "<your-database-password>"
$env:JWT_SECRET = "<base64-encoded-secret-key>"
.\mvnw.cmd spring-boot:run
```

Do not put real credentials or signing keys in source control. Generate a strong
random key and keep it stable across application instances; changing the key
invalidates existing tokens. The checked-in property file includes a
development signing-key value, so override it before running outside local
development. For production, review the schema-management strategy and disable
SQL statement logging unless it is explicitly required.

## Authentication

`POST /api/auth/register` and `POST /api/auth/login` are public. All other routes,
including logout, require the `Authorization` header to use the bearer scheme
with the token returned by login.

Tokens contain the employee ID as their subject and expire according to
`jwt.expiration`. The security filter resolves the employee from the database
for authenticated requests. Requests use stateless sessions; the server does
not use a browser session or issue refresh tokens.

### Registration and login flow

1. Seed a department in the `departments` table.
2. Register an employee using that department's code.
3. Log in using the employee ID and password.
4. Pass the returned token in the `Authorization` header for protected routes.
5. Call logout with that token to blacklist it in this running server process.

## REST API

Base URL for local development: `http://localhost:8080`.

### Register

`POST /api/auth/register` — public.

Request:

```json
{
  "employeeId": "E1001",
  "name": "Avery Employee",
  "email": "avery@example.com",
  "departmentCode": "ENG",
  "password": "choose-a-password"
}
```

All fields are required and non-blank; `email` must be a valid email address.
Employee ID and email must be unique, and the department code must already
exist.

Success (`200 OK`, text response):

```text
Registration successful
```

### Log in

`POST /api/auth/login` — public.

Request:

```json
{
  "employeeId": "E1001",
  "password": "choose-a-password"
}
```

Both fields are required and non-blank.

Success (`200 OK`):

```json
{
  "message": "Login successful",
  "token": "<jwt>",
  "employeeId": "E1001",
  "name": "Avery Employee"
}
```

### Log out

`POST /api/auth/logout` — authenticated.

Send the current token in the bearer header. The endpoint returns
`Logout successful` as a text response. It adds the token to an in-memory
blacklist; a server restart clears that blacklist.

### Get dashboard

`GET /api/dashboard` — authenticated.

Success (`200 OK`):

```json
{
  "name": "Avery Employee",
  "department": "Engineering",
  "attendancePercentage": 0.0,
  "performanceScore": 0.0
}
```

Attendance and performance values are initialized to zero at registration.
This API currently has no endpoint for changing them.

### Get own profile

`GET /api/profile` — authenticated.

Success (`200 OK`):

```json
{
  "employeeId": "E1001",
  "name": "Avery Employee",
  "email": "avery@example.com",
  "departmentCode": "ENG",
  "departmentName": "Engineering"
}
```

### Change own password

`PUT /api/profile/password` — authenticated.

Request:

```json
{
  "currentPassword": "old-password",
  "newPassword": "new-password"
}
```

Both fields are required and non-blank. The new password must contain at least
six characters and must differ from the current password. The current password
is verified before the new BCrypt hash is saved.

Success (`200 OK`, text response):

```text
Password changed successfully
```

### List employees in own department

`GET /api/employees/department` — authenticated.

Success (`200 OK`): a JSON array of employee profiles for the caller's
department. The array may be empty.

### Get an employee in own department

`GET /api/employees/{employeeId}` — authenticated.

Example: `GET /api/employees/E1002`.

Success (`200 OK`): one employee profile using the same fields as
`GET /api/profile`. Requests for employees outside the caller's department are
reported as not found.

### List departments

`GET /api/departments` — authenticated.

Success (`200 OK`): array of departments. The API does not currently provide
department create, update, or delete operations.

```json
[
  {
    "id": 1,
    "departmentCode": "ENG",
    "departmentName": "Engineering"
  }
]
```

### List employees in a department

`GET /api/departments/{departmentId}/employees` — authenticated.

Example: `GET /api/departments/1/employees`.

Success (`200 OK`): array of employee profiles using the fields shown in
`GET /api/profile`. A missing department returns `404 Not Found`.

### Get an employee in a department

`GET /api/departments/{departmentId}/employees/{employeeId}` — authenticated.

Example: `GET /api/departments/1/employees/E1002`.

Success (`200 OK`): one employee profile. The employee must belong to the
specified department; otherwise the API returns `404 Not Found`.

### Get attendance for today

`GET /api/attendance/today` — authenticated.

Success (`200 OK`):

```json
{
  "id": 1,
  "date": "2026-10-07",
  "checkIn": "2026-10-07T09:00:00",
  "checkOut": null,
  "status": "PRESENT"
}
```

If the signed-in employee has not checked in today, the API returns
`404 Not Found`.

### Check in

`POST /api/attendance/check-in` — authenticated; no request body.

Success (`200 OK`): returns the attendance object in the same format as
`GET /api/attendance/today`. Only one attendance record can be created per
employee per day. A second check-in on the same day returns `400 Bad Request`.

### Check out

`POST /api/attendance/check-out` — authenticated; no request body.

Success (`200 OK`): returns the updated attendance object. The employee must
have checked in first, and check-out is allowed at least 60 seconds after
check-in. Missing check-in, duplicate check-out, or an attempt before 60 seconds
returns `400 Bad Request`.

### Get attendance percentage

`GET /api/attendance/percentage` — authenticated.

Success (`200 OK`):

```json
{
  "attendancePercentage": 100.0
}
```

The calculation is based on the signed-in employee's recorded attendance
statuses. It returns `0.0` when there are no attendance records.

### Get attendance history

`GET /api/attendance/history` — authenticated.

Success (`200 OK`): array of attendance objects in the same format as
`GET /api/attendance/today`, sorted by date descending. The array may be empty.

### Create a task

`POST /api/tasks` — authenticated.

Request:

```json
{
  "taskName": "Review monthly payroll",
  "completionPercentage": 35,
  "employeeId": "E1002"
}
```

All fields are required. `completionPercentage` must be an integer from `0`
through `100`. The employee ID must identify an existing employee in the
signed-in employee's department. Tasks are assigned to the employee ID in the
request, not necessarily to the caller. A missing employee or an employee in a
different department returns `404 Not Found`.

Success (`200 OK`):

```json
{
  "id": 7,
  "title": "Review monthly payroll",
  "description": "Completion: 35%",
  "status": "IN_PROGRESS",
  "dueDate": "2026-10-14"
}
```

The API sets the due date to seven days from the server's current date. A
completion percentage of `100` sets status to `COMPLETED`; all other accepted
values set it to `IN_PROGRESS`. The current task response does not expose a
separate `completionPercentage` field; the submitted percentage is stored in
the task description.

### List my tasks

`GET /api/tasks` — authenticated.

Success (`200 OK`): array of task objects in the same format as the create-task
response. It returns tasks assigned to the signed-in employee. The array may be
empty.

### Get one of my tasks

`GET /api/tasks/{taskId}` — authenticated.

Example: `GET /api/tasks/7`.

Success (`200 OK`): one task object. A task not found or not assigned to the
signed-in employee returns `404 Not Found`.

Task updates and deletion are not currently implemented.

### Common response and status behavior

| Status | Meaning |
| --- | --- |
| `200 OK` | Request succeeded. |
| `400 Bad Request` | Invalid request fields, duplicate registration details, invalid department, attendance rule violation, or incorrect current password. |
| `401 Unauthorized` | A token explicitly found in the in-memory blacklist is rejected with this status. |
| `404 Not Found` | The requested employee or resource was not found, including an employee or task outside the caller's allowed scope. |

The global exception handler returns business/not-found errors in JSON:

```json
{
  "error": "Employee not found"
}
```

Validation errors are returned as a JSON object keyed by invalid field, for
example:

```json
{
  "employeeId": "Employee ID is required"
}
```

Spring Security handles authentication failures separately; their response
shape is not customized by this application. Requests without a valid
authenticated principal are denied; do not rely on a specific response body.

## Data model

### `departments`

| Column | Description |
| --- | --- |
| `id` | Generated primary key. |
| `department_code` | Required, unique department code used during registration. |
| `department_name` | Required display name. |

### `employees`

| Column | Description |
| --- | --- |
| `id` | Generated primary key. |
| `employee_id` | Required, unique business identifier and login name. |
| `name` | Required employee name. |
| `email` | Required, unique email address. |
| `password_hash` | Required BCrypt password hash; never returned by the API. |
| `department_id` | Required reference to a department. |
| `attendance_percentage` | Attendance value; initialized to `0.0`. |
| `performance_score` | Performance value; initialized to `0.0`. |

### `attendance`

| Column | Description |
| --- | --- |
| `id` | Generated primary key. |
| `employee_id` | Required reference to the employee. |
| `attendance_date` | Required date of the attendance record. |
| `check_in` | Check-in date and time. |
| `check_out` | Check-out date and time, if checked out. |
| `status` | Required status; check-in currently records `PRESENT`. |

There is a unique constraint on `employee_id` and `attendance_date`, allowing
one attendance record per employee per day.

### `tasks`

| Column | Description |
| --- | --- |
| `id` | Generated primary key. |
| `title` | Required task name. |
| `description` | Task description; task creation currently stores the submitted completion percentage here. |
| `status` | Required status (`IN_PROGRESS` or `COMPLETED` when created through the API). |
| `due_date` | Due date assigned by the API to seven days after creation. |
| `employee_id` | Required reference to the assigned employee. |

## Errors and validation

Request DTO validation occurs for registration, login, password change, and task
creation.
`@NotBlank` fields reject empty or whitespace-only strings. Email syntax is
checked during registration; a six-character minimum is enforced for a new
password; task completion percentage must be between 0 and 100. No stronger
password policy is currently implemented.

Service-level checks reject duplicate email/employee IDs and unknown department
codes. These checks produce `400 Bad Request`; missing employee resources
produce `404 Not Found`.

## Operational and security notes

- The logout blacklist is held in process memory. It is not shared between
  instances and is cleared on restart; use persistent/shared revocation storage
  if logout must remain effective across restarts or a cluster.
- Authentication uses employee IDs, while protected service lookups resolve the
  authenticated employee's email from the security principal.
- Do not expose MySQL credentials or JWT signing keys in source control, logs,
  issue reports, or client applications.
- Use HTTPS in deployed environments to protect bearer tokens in transit.
- `spring.jpa.hibernate.ddl-auto=update` and SQL logging are development-oriented
  defaults; review both before production use.
- No CORS policy is configured by this server. Configure and validate an
  explicit origin policy before browser clients on a different origin call it.
- No admin authorization or role-based restrictions are implemented; all
  authenticated users share the employee endpoints, with employee lookup
  limited to their own department.
